Hi, I'm Rahul Nandanwar, student ID 2026NS93095. This is my demo for Assignment 1 of AI Augmented SDLC, on spec-driven development and harness engineering. I built two small applications with GitHub Spec Kit. Part 1A is SplitKaro, a deterministic expense splitter. Part 1B is TxnSense, a Gemini-powered parser for bank and UPI SMS messages. ## 1a
Here is SplitKaro. Each behaviour traces to an acceptance criterion in the spec. AC-008, for example, says that leftover paise go to members in alphabetical order, and AC-025 fixes the exact settle-up output. I create a group, add a nine hundred rupee dinner and a hundred rupee snack, and list the expenses. The hundred rupees cannot be split evenly, so the extra paisa goes to Asha, first in alphabetical order, which is why her balance ends in thirty four. The balances always add up to zero, and settle gives a short, deterministic list of payments. If someone tries to pay more than they owe, the payment is rejected with exit code four. Now the harness. One command runs six independent gates: an integrity lock on the spec and tests, Ruff, Bandit, a hundred and seven spec-derived tests including property tests, coverage at least ninety per cent, and acceptance-criteria traceability. Everything passes. The very first run failed, though. The package was not importable because macOS had hidden the virtual environment's path files, and Ruff flagged the import order in three test files. That structured feedback went back to the coding agent, which fixed the root cause without touching any assertion, and the same gates then passed. The git history shows every Spec Kit step as its own commit.

## 1b
Part 1B is TxnSense. The model's wording can vary, so the spec fixes a JSON schema, invariants, safety guardrails and an evaluation threshold, all before the first evaluation. A normal UPI debit comes back as a structured transaction with amount, merchant, category and date. A KYC phishing message is flagged as high risk, and the link and phone number are never echoed. The harness runs twenty-five cases through three layers: schema validation, invariant and guardrail checks, then field accuracy plus an independent LLM judge, Gemma, that grades the summary. The first evaluation failed. The model labelled an OTP message that also named an amount and a merchant as a plain OTP, while my clarified spec says that is a transaction. The safety pass rate was below one hundred per cent, so the run failed. The feedback file went to the coding agent, the prompt got an explicit precedence rule, and the identical harness then passed every threshold.
